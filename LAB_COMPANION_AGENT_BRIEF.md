# Physics 2 Lab Companion: Build Brief for the Implementing Agent

You are building a lab companion web app for a team of three university students. They are taking a Physics 2 laboratory and are aiming for a grade of 10/10. You will receive two inputs: this brief and the lab guide PDF (`LaboratoryGuide.pdf`). Read this brief to the end first. Then read the PDF to the end. Then plan, and only after that build.

---

## 0. Mission in one paragraph

Build a mobile-first Progressive Web App (PWA) called **Lab Companion** that also works well on tablets and laptops. It covers **Experiments 5, 6, 7, 3 and 4** of the lab guide, in that order, because that is the order the team will run them. It has three features:

1. **Calculator (multitool).** A high-accuracy computation engine with generic tools: least squares, uncertainty propagation, counting statistics, rounding to the lab's significant-figure rule, and more. It also has one end-to-end analysis pipeline per experiment that turns raw measurements into the exact result tables and conclusions the guide asks for.
2. **Experiment guides.** These are fast "dummy" step-by-step run guides, split by role for three people. Data entry happens inline at the step where each number is produced.
3. **Answers.** A complete, defensible answer key for every question in sections X.8 of Experiments 3–7, plus the "explain why" prompts embedded in the procedures. Every number in it is generated by the engine, not typed by hand.

Out of scope: Experiments 1, 2 and 8. You should still read them, because they share conventions (see §1).

### Quality bar

The user expects excellence. Measure everything you do against these four questions.

- **Correct:** Is every formula, unit and number right, and verified by a test?
- **Complete:** Is every step, table, analysis item, uncertainty item, conclusion and question in the guide covered for Experiments 3–7?
- **Fast in the lab:** Can a stressed student, holding a phone in one hand in a dark room, follow a step and enter a number in under 10 seconds?
- **Defensible:** Can the team explain every result to the professor? This means showing the work, flagging where the guide has typos, and labelling clearly any improvement that goes beyond the guide.

## 3. Architecture and technology choices

### 3.1 Decision summary

| Layer | Choice | Why |
|---|---|---|
| Computation engine | **Python 3.12 package `labcalc`**, built on **mpmath** (arbitrary-precision decimal floating point). **SymPy** is lazy-loaded, only for the custom-expression propagation tool. | Arbitrary precision removes floating-point error from the result path. Python has the best-validated scientific ecosystem for cross-checking. The same code runs natively under pytest and in the browser. |
| Engine runtime in the browser | **Pyodide** (CPython compiled to WebAssembly), running in a **dedicated Web Worker** | Runs offline with no server, never blocks the UI thread, and executes the exact code that the native tests verified. |
| Front end | **Vite + React + TypeScript**; Tailwind (or CSS modules); **KaTeX** for formulas; a lightweight touch-friendly chart library (uPlot or Chart.js; pick one) | Fast to build, strong mobile support, and type safety for the engine API contract. |
| Offline/PWA | `vite-plugin-pwa` (Workbox). **Self-host the Pyodide distribution files** in the build and precache them. | Must work in airplane mode in the lab. Do not depend on a CDN at lab time. |
| Persistence | IndexedDB (`idb-keyval` or Dexie), with autosave on every edit | Data must survive a phone lock, a reload or a crashed tab. |
| Hosting | Any static host (GitHub Pages, Netlify or Cloudflare Pages) | No backend is needed. |
| Tests | pytest + hypothesis (engine); Vitest (UI logic); Playwright (end-to-end flows on mobile viewports) | See §4.6 and §11. |

Production results must not use NumPy or SciPy. They are allowed **only in tests** (and optionally in the Monte Carlo tool) as an independent cross-check.

### 3.2 Hard rules for the data flow

- The UI collects **strings**, never JavaScript `Number`s, and sends them to the worker. The engine parses them directly into mpmath values. **JavaScript never does arithmetic on results.** Floats are allowed only for chart drawing coordinates.
- The engine returns JSON. Each numeric result is returned as a decimal string with about 30 significant digits, along with its uncertainty string, its unit, a ready-to-paste report string, and a LaTeX string.
- **Cold-start trade-off.** The first load downloads roughly 10–20 MB (Pyodide plus mpmath, and SymPy later). Starting Pyodide takes a few seconds on a phone. To handle this:
  - Start warming up the worker the moment the app opens.
  - Show an "Engine ready" indicator.
  - Make sure guides, answers and data entry never wait for the engine.
  - Keep SymPy out of the initial load. Load it only when the custom propagation tool is opened.
- Document the decision and its alternatives (a FastAPI backend, or JavaScript with decimal.js) in `docs/DECISIONS.md`.

### 3.3 Suggested repository layout

```
/engine/labcalc/        # Python package (pure Python + mpmath)
  parse.py  stats.py  counting.py  linfit.py  propagate.py  montecarlo.py
  rounding.py  constants.py  units.py  graphical.py  decay.py
  experiments/exp3.py exp4.py exp5.py exp6.py exp7.py
```

## 4. Computation engine specification

### 4.1 Numerical policy (the accuracy contract)

1. **Exact input parsing.** Convert each string to an mpmath `mpf` from its decimal string. Never go through a float.
2. **Working precision.** Use `mp.dps = 50` for all calculations. In test mode, and as an optional "self-check" toggle in Settings, recompute every pipeline at `mp.dps = 100`. Assert that the two results agree to at least 40 significant digits.
3. **Stable algorithms, even at high precision.** For regression, use centred two-pass sums such as Σ(xᵢ − x̄)². In the "show your work" steps, display the guide's raw-sum formulas (S_x, S_xx, S_xy, ... from Appendix B), because that is what students are taught. The two forms are algebraically identical.
4. **No intermediate rounding.** Round only for display and reporting.
5. **Two constant sets**, selectable globally and shown on every result:
   - **CODATA (default):** exact SI 2019 constants plus CODATA 2022. See §7.
   - **Guide constants:** the rounded values the PDF uses (for example e = 1.6×10⁻¹⁹ C, h = 6.626×10⁻³⁴ or 6.63×10⁻³⁴ J·s, mₑ = 9.1×10⁻³¹ kg). These let students reproduce the guide's numbers, such as the 3.3×10⁻¹⁰ in eq. 4.8.
6. **Units.** Normalise to SI at the input boundary. Each tool declares its input and output units, and the UI offers convenient display units (nm, cm⁻¹, kBq, kV, cm²/g). Unit conversions get unit tests.
7. **Show your work.** Every tool returns an ordered list of steps. Each step contains the formula in LaTeX, the formula with numbers substituted (sensibly rounded), and the result. Students copy these into their reports, and the professor will want to see the calculation.
8. **Honest warnings.** The engine returns warnings for situations such as these:
   - n < 3 points in a fit;
   - a zero or negative count rate after background subtraction;
   - an extrapolation outside the calibration range (Experiment 3, Hα and Hε);
   - an approximation used outside its validity range (Experiment 5 near positions, Experiment 4 large rings);
   - an outlier, defined as a standardised residual above a threshold, default 2.5.

Note on what "accuracy" means here. Floating-point error is never what limits a lab result. The real risks are wrong formulas, wrong units, ignored covariances, wrong rounding and misidentified spectral lines. Arbitrary precision is cheap insurance. Correctness tests (§4.6) and domain checks (the "sanity values" in §6) are where accuracy is actually won.

### 4.2 The lab's rounding rule

The guide (§2.8 and §5.8 notes, quoting GUM 7.2.6) says to report **the uncertainty with 1 significant digit, or 2 significant digits if that first digit is 1**. Round the value to the **same decimal position** as the uncertainty.

Implementation rules:

- Use Python `decimal` with `ROUND_HALF_UP`, not banker's rounding.
- Decide the number of significant digits from the **leading digit of the unrounded uncertainty**. If rounding then carries over (0.096 → 0.1), keep the carried result.
- Provide an optional setting, "round uncertainty up". GUM permits it, but it is off by default.
- Prefer scientific notation with a shared exponent, for example `(1.235 ± 0.002)×10⁴ Bq`, so that trailing zeros are never ambiguous.
- If the uncertainty is zero or missing, show a warning instead of a fake precision.

Required unit tests:

| Value | Uncertainty | Rounded uncertainty | Reported |
|---|---|---|---|
| any | 0.096 | 0.1 | |
| any | 0.0149 | 0.015 | |
| any | 0.15 | 0.15 | |
| any | 1.96 | 2.0 | |
| any | 19.6 | 20 | |
| 12345.678 | 23 | 2×10¹ | (1.235 ± 0.002)×10⁴ |
| 6.62607015×10⁻³⁴ | 0.4×10⁻³⁵ | 4×10⁻³⁶ | (6.626 ± 0.004)×10⁻³⁴ |

### 4.3 Generic tools (Calculator tab)

Each tool gets a mobile form, a results card, and a "show steps" panel.

**G1. Descriptive statistics.** Inputs are a list of numbers. Outputs:
- n, mean, minimum and maximum;
- sample standard deviation with N−1;
- standard error of the mean, s/√N.

Note that Appendix A eq. A.1 uses 1/N with the *true* mean. The N−1 form applies when the experimental mean is used.

**G2. Counting statistics (Appendix A.3).** Outputs:
- σ_N = √N for a count N;
- rate n = N/t and σ_n = √N/t;
- background-subtracted rate n = n′ − n_b, with σ = √(σ_n′² + σ_nb²);
- ratios and products of rates;
- a **counting-time planner**: the time needed to reach a target relative precision ε is t ≈ 1/(n·ε²). This helps the team decide between 60 s and 100 s counts.

**G3. Linear least squares (Appendix B).** The default model is y = a·x + b. Outputs:
- a and b;
- s_a and s_b (eqs. B.4/B.5, equivalently B.9–B.11);
- **cov(a,b) = −x̄·s_a²** (unweighted case);
- correlation coefficient r and R²;
- residuals and standardised residuals, with outlier flags.

Variants:
- **Through the origin** (y = a·x): a = Σxy/Σx² and s_a² = SSR/((n−1)·Σx²).
- **Weighted**, given σ_yᵢ: report both the internal (σ-based) and the external (χ²_red-scaled) uncertainty, plus χ²_red.
- **Inverse prediction**, for calibration: x₀ from a measured y₀, with an uncertainty that includes cov(a,b) and σ_y₀.

Require n ≥ 3, since there are n − 2 degrees of freedom.

**G4. Uncertainty propagation.**
- **Quick rules**, matching Experiment 2 Q3: σ for f = x ± y; relative σ for f = x·y, f = x/y, f = xᵏ and f = c·x.
- **General tool.** The user types an expression such as `sqrt(B/(x-A))`, the variables with their values and σ's, and an optional correlation or covariance matrix. SymPy computes the partial derivatives and mpmath evaluates them. Show the **uncertainty budget**: each term's contribution as a percentage of σ_f².
- **Monte Carlo cross-check** (GUM Supplement 1): run 10⁵–10⁶ samples. Report the mean, standard deviation and 95% interval. Warn if the result differs from linear propagation by more than 10%, because that signals strong non-linearity.

**G5. Graphical-method helper.** The guide asks for results "from the analysis of the graph" in Experiments 6 and 7, and Experiment 6 Q6 compares them with least squares.
- **Slope from a drawn line:** the user enters two points read off their hand-drawn best-fit line, P₁ and P₂, chosen far apart. The tool returns the slope and intercept.
- **Max/min slope method:** this gives the graphical uncertainty as σ ≈ (a_max − a_min)/2.
- **Axis-scale suggester for A4 millimetre paper.** Given the data range, it proposes round scales (1, 2 or 5 × 10ᵏ units per cm) so that the data fill at least two-thirds of the sheet. It also states the origin and units for each axis.

**G6. Report formatter and comparison.**
- Applies the rounding rule from §4.2.
- **Comparison with a reference value:** relative deviation (%) and z = |x − x_ref| / √(σ² + σ_ref²), with the verdict "compatible" when z ≤ 2. Use this for every "Compare your results with…" line in the guide.
- **Comparison of two of the team's own values:** for example graphical versus least squares in Experiment 6 Q6, or Method I versus Method II in Experiment 5.

**G7. Units and constants.**
- Conversions: eV ↔ J; nm ↔ Hz ↔ eV ↔ cm⁻¹ (hc = 1239.84198… eV·nm); Bq ↔ Ci; mm, cm and m; g/cm³; kV.
- A constants table that shows each constant's source and year.

**G8. Radioactive decay correction.** A(t) = A₀·2^(−Δt/T½), with Cs-137 T½ = 30.08 y (verify with NNDC). Use it if the Experiment 5 source has a labelled reference activity and date. Ask the professor whether it does.

Each experiment gets a pipeline with these stages:

input schema → derived columns → fits → results → uncertainties → conclusions table (exactly as in the guide) → plots → steps → warnings → "Advanced" extras

The pipelines are specified in §6.

```ts

{ id: string, tool: "linfit" | "propagate" | "exp5.analyze" | ..., params: {...}, constants: "codata" | "guide" }
// response
{ id, ok: true, result: { values: {name: {value: string, unc?: string, unit: string, report: string, latex: string}},
                          tables: [...], plots: [...series...], steps: [{latex, substituted, result}], warnings: [string] } }
| { id, ok: false, error: {code, message, field?} }
```

Add a TypeScript type for every tool's params and result. Generate these types from a single JSON Schema if practical.

### 4.6 Validation. All of these must pass.

- **NIST StRD linear-regression certified datasets.** Download from `https://www.itl.nist.gov/div898/strd/` and do not type the values from memory.
  - **Norris** tests y = b₀ + b₁x.
  - **NoInt1** and **NoInt2** test the through-origin fit.
  - The estimates *and* their certified standard deviations must match to **at least 12 significant digits**. They are certified to about 15.
- **Independent cross-checks**, in tests only:
  - least squares against `numpy.polyfit` and `scipy.stats.linregress`, to at least 10 digits on well-conditioned random data;
  - propagation against the `uncertainties` package;
  - Monte Carlo against linear propagation on linear functions, within Monte Carlo noise.
- **Golden synthetic datasets, one per experiment.**
  - Generate data from a known truth (for example d₁ = 2.13×10⁻¹⁰ m, Λ = 1.0×10⁵ Bq, h = 6.62607015×10⁻³⁴ J·s, R = 1.0967758×10⁷ m⁻¹, μ_Pb = 1.25 cm⁻¹).
  - With zero noise, the pipeline must recover the truth to at least 30 digits.
  - With Gaussian or Poisson noise, the recovered value must fall within about 2σ of the truth in at least 95% of 1,000 seeded trials. This checks that the reported uncertainties are honest.
- **Precision self-check:** results at dps = 50 and dps = 100 must agree.
- **Rounding-rule edge cases** from §4.2.
- **Parser tests:** `1,5`, `1.5e-3`, `1.5×10^-3`, `−2`, `" 3 "`. Empty input, `1,2,3` and `abc` must give a clear field-level error.
- **Snapshot tests for every number in the Answers** (§6, each part J). Answers are generated by the engine at build time and frozen. A diff must fail CI.
- **Dimension sanity:**
  - d in Experiment 4 is around 10⁻¹⁰ m;
  - R in Experiment 3 is around 10⁷ m⁻¹;
  - h in Experiment 7 is around 10⁻³⁴ J·s;
  - μ in Experiment 6 is around 0.1–2 cm⁻¹;
  - Λ in Experiment 5 is greater than 0.

### 6.1 Experiment 5: Source activity by the solid-angle method (scintillation detector)

**A. What is measured.** The activity Λ of a ¹³⁷Cs source, using

n = Λ · (Ω/4π) · ε · S

with the guide's values ε = 0.2, S = 1 and detector-face diameter D = 2.54 cm.

The solid angle is:
- **exact:** Ω/4π = ½ − 1/√(4 + (D/r)²);
- **approximate**, for r ≫ D: Ω/4π ≈ D²/(16r²).

**B. Before the lab.**
- Answer Q3 and Q4. The guide's analysis needs them.
- Know the counter buttons from Fig. 5.2: Start, Stop, Reset, On/Off.
- Research the "NP 632" counter. If you cannot find a manual, keep the instructions generic and mark them "Verify in lab".

**D. Run guide (draft).**

1. *(All, 1 min)* Identify the parts:
   - the scintillation detector with its photomultiplier, mounted vertically in the rack;
   - the rack slots, which set the source-to-detector distance;
   - the plastic source tray;
   - the lead shield;
   - the digital counter.
2. *(OP)* Turn the counter on. Make sure no source is nearby. Set up a **600 s background** count and press Start. ⏱ 10 min.
   - **Meanwhile:** do step 3.
3. *(RD + AN, during the background count)* For every slot, measure the **distance r from the detector face to the source position**, meaning the tray surface where the source sits.
   - Use a ruler or caliper.
   - Measure each distance twice, and get two different people to read it.
   - Write down the resolution of the tool you used.
   - Enter each slot as a row in the app.
4. *(RD)* When the background count ends, record N_b and t_b = 600 s.
5. *(OP)* Ask the professor or assistant for the source and follow their handling instructions.
6. *(OP)* Put the source on the tray, centred. Slide the tray into a slot. Put the lead shield in place.
7. *(RD)* Count for **100 s**.
   - The guide allows 60–100 s. Use 100 s unless time is very short, because it gives better statistics.
   - Record N and t.
   - **Decision:** if a far slot gives fewer than about 1,000 counts, consider a longer count. The app's counting-time planner tells you how long.
8. Repeat steps 6–7 for **every available slot**.
   - AN watches the live plot of n against D²/(16r²).
   - The far points should lie on a straight line. The nearest points will bend *below* the line. **This is expected**, because the approximation fails at short distances. It is not a measuring error.
9. *(Optional, if time allows)* Repeat one position to check reproducibility.
10. Hand the source back as instructed. Switch everything off.

**E. Data schema.**

Background: {N_b, t_b}.

Rows: {slot, r (cm), t (s), N}.

Derived columns:
- σ_N = √N
- n′ = N/t
- σ_n′ = √N/t
- n = n′ − n_b
- σ_n = √(σ_n′² + σ_nb²)
- X_approx = D²/(16r²)
- X_exact = ½ − 1/√(4 + (D/r)²)

These columns match the guide's example table: r, t, N, σ_N, n′, σ_n′, n, σ_n.

**F. Analysis pipeline.**

The guide's ordered steps are:
1. Answer Q3 and Q4.
2. Plot n = f(r) and estimate Λ using Q4 (Method I).
3. Plot n = f(D²/16r²) and estimate Λ using eq. 5.3 (Method II).

- **Method I ("graph n = f(r), use Q4").**
  - At r → 0, Ω → 2π, so Ω/4π = ½ and n(0) = Λ·½·ε·S. Therefore Λ_I = 2·n(0)/(ε·S).

**J. Answer key (draft).**

- **Procedure step 2: explain eq. 7.3.**
  1. One photon of energy hν is absorbed by one electron.
  2. The electron spends W to escape the cathode. The most energetic electrons leave with K_max = hν − W.
  3. The emitted electrons charge the capacitor, so the anode becomes negative relative to the cathode, building up a retarding voltage U.
  4. Only electrons with K > eU can still reach the anode.
  5. Charging stops at U₀, when even the fastest electrons are turned back. Therefore e·U₀ = K_max = hν − W.
  - Note: experimentally, W effectively includes the contact potential.
- **Q1 (relation between K and ν).**
  - Einstein's relation: K_max = h·ν − W.
  - The dependence is **linear (affine)**, increasing with slope h. It is not proportional, because of the −W term.
  - K_max does not depend on the light's intensity.
  - There is no emission below ν₀ = W/h.
- **Q2 (what each element in Fig. 7.1 does).**
  - Lamp: the light source, giving discrete Hg lines.
  - Lens: focuses the light onto the photocell.
  - Diaphragm: controls the intensity.
  - Filter wheel: selects a single Hg line, i.e. one frequency.
  - Photocell: emits the photoelectrons.
  - Extra rows: the capacitor circuit with its discharge switch, and the voltmeter.
  - Map each to the letters A–E **after checking in the lab**.
- **Q3 (mean and standard deviations).**
  - Mean: x̄ = (1/N)·Σxᵢ, with N = 10.
  - Standard deviation of the data: s = √[Σ(xᵢ − x̄)²/(N − 1)].
  - Standard deviation of the mean: s_x̄ = s/√N.
- **Q4 (the electronvolt).** It is the energy an electron (charge e) gains when accelerated through a potential difference of 1 V. 1 eV = 1.602176634×10⁻¹⁹ J, exact.
- **Q5 (an electron accelerated from rest).** The engine computes these. Check the non-relativistic formula against the relativistic one.

  | U | K | v | v/c |
  |---|---|---|---|
  | 10 V | 10 eV = 1.602×10⁻¹⁸ J | ≈ 1.876×10⁶ m/s | ≈ 0.006256 |
  | 100 V | 100 eV = 1.602×10⁻¹⁷ J | ≈ 5.931×10⁶ m/s | ≈ 0.01978 |
  | 10⁸ V | 100 MeV = 1.602×10⁻¹¹ J | relativistic | ≈ 0.9999871 |

  For 10⁸ V, the **relativistic formula is mandatory**: γ = 1 + eU/(mₑc²) ≈ 196.7, and v/c = √(1 − 1/γ²). The classical formula would give v ≈ 5.93×10⁹ m/s ≈ 19.8c, which is impossible.
- **Q6 (lowest frequency, longest wavelength).**
  - ν_min = ν₀ = −b/a, from the fit, with an uncertainty that includes cov(a,b). λ_max = c/ν₀.
  - **Meaning:** this is the threshold (cut-off) frequency of the photocathode, with W = h·ν₀. Light below it ejects no electrons, however intense it is. This was the classical paradox that the photon picture resolves.

### 6.5 Experiment 4: Electron diffraction by polycrystalline graphite

**A. What is measured.** The graphite lattice-plane spacings d₁ and d₂. They come from the diameters D of the first two diffraction rings, measured at several accelerating voltages U, using

D = (2Lh/√(2mₑe)) · U^(−1/2) / d

with L = 13.5 cm. In SI units this is D ≈ 3.3×10⁻¹⁰ · U^(−1/2) / d, which is eq. 4.8 of the guide.

**B. Before the lab.**
- Know the expected ring sizes, so you recognise the rings (see H).
- Find out what measuring tool the lab provides: a vernier caliper or a flexible ruler.
- Make sure the room can be darkened.

**D. Run guide (draft).**

⚠ Safety (always visible on this experiment's run screen):
- **Never exceed 5 kV.** Above that, X-rays are produced.
- **Do not touch the tube or the cables.** High voltage is present.
- **No mechanical stress on the tube.** It can implode.
- **The bright central spot damages the screen.** Lower U immediately after each reading.

1. *(OP)* With the supply **off**, turn the U knob fully left (to 0).
2. *(OP)* Switch the supply **on**. Wait **about 1 minute** for the cathode to stabilise.
3. *(OP)* Raise U slowly until the rings appear (typically around 2–3 kV). **You should see** a bright central spot surrounded by two concentric rings.
4. Plan **at least 5 voltages**. Recommended: **3.0, 3.5, 4.0, 4.5 and 5.0 kV**. These match Q3's table. Add 2.5 kV if the rings are clearly visible there.
5. At each U:
   1. OP sets U and RD reads the display.
   2. RD measures the **inner and outer diameters** of ring 1 and ring 2 with the caliper held against the bulb, through the centre. Read quickly.
   3. AN enters the values.
   4. OP **lowers U right away**.
   - If time allows, a second person measures the same rings independently, and the app averages the readings.
6. *(OP)* Turn U down to 0. Switch off and unplug.

**E. Data schema.**

Rows: {U (kV), D₁_in, D₁_out, D₂_in, D₂_out (cm)}.

Derived columns: D₁ = (D₁_in + D₁_out)/2, D₂ = (D₂_in + D₂_out)/2, and U^(−1/2) in V^(−1/2).

These match the guide's table.

**F. Analysis pipeline.**

1. For each ring, fit D (in m) against U^(−1/2) (in V^(−1/2)) by least squares. This gives a slope k.
2. Then **d = C/k**, with C = 2Lh/√(2mₑe).
   - With CODATA constants, C ≈ 3.311×10⁻¹⁰ m·V^(1/2).
   - The guide gives 3.3×10⁻¹⁰. Show both values, and use CODATA by default.
3. Check that the intercept is close to 0. Also show the through-origin fit.
4. **Q7 linearisation as a cross-check:** U is linear in D⁻², with slope C²/d², so d = C/√slope.
5. **Advanced:**
   - **Exact geometry:** 2θ = arctan(D/2L) and d = λ/(2·sin θ), instead of the small-angle approximation.
   - **Relativistic wavelength:** λ = h/√(2mₑeU·(1 + eU/(2mₑc²))).
   - **Spherical-bulb correction:** research the manufacturer's manual. L = 13.5 cm suggests a Leybold-type tube (555 626); verify this.
6. **Conclusions:** d₁ and d₂ with their uncertainties. Compare with 2.13×10⁻¹⁰ m and 1.23×10⁻¹⁰ m.

**G. Uncertainty.**
- σ_d = d·(s_k/k), treating C as exact.
- Optionally add σ_L in quadrature.

**H. Sanity values.**
- Expected ring sizes:
  - at 3 kV: D₁ ≈ 2.8 cm and D₂ ≈ 4.9 cm;
  - at 5 kV: D₁ ≈ 2.2 cm and D₂ ≈ 3.8 cm.
- **Live check: D₂/D₁ ≈ √3 ≈ 1.73 at every U.** In graphite, d₁ = a·√3/2 and d₂ = a/2, with a ≈ 2.46 Å. Display this ratio as each row is entered.

**I. Pitfalls.**
- Parallax when measuring with the caliper on curved glass.
- Fuzzy ring edges. Define inner and outer edges consistently.
- Lingering at high U, which burns the screen.
- Forgetting the unit conversions: cm to m, kV to V.

**J. Answer key (draft).**

- **Q1 (grain of sand).**
  - m = 3×10⁻⁸ g = 3×10⁻¹¹ kg and v = 340 m/s, so p = 1.02×10⁻⁸ kg·m/s.
  - λ = h/p ≈ 6.5×10⁻²⁶ m.
  - That is about 3×10⁻¹⁶ times the carbon atomic diameter (2.2×10⁻¹⁰ m) and d₁.
  - **No diffraction is possible.** No structure is small enough to diffract it.
- **Q2 (electron at 2 kV).**
  - λ = h/√(2mₑeU) ≈ 2.74×10⁻¹¹ m (27.4 pm). The relativistic value is about 27.4 pm, about 0.1% smaller.
  - This is about 8 times smaller than d₁, but of the same order of magnitude, and Bragg's condition λ ≤ 2d can be satisfied.
  - **Yes, diffraction is possible.**
- **Q3 (table for U = 3.0 to 5.0 kV in steps of 0.5 kV).**
  - Columns: v (non-relativistic and relativistic), v/c, and λ (non-relativistic and relativistic).
  - v/c ranges from about 0.108 to 0.14. The relativistic correction is about 0.15–0.25% in λ and about 0.4–0.7% in v.
  - **Was the non-relativistic formula acceptable?** Yes, because these corrections are smaller than the experimental uncertainty. Report the actual numbers.
- **Q4 (how the experiment confirms de Broglie's hypothesis).**
  - The ring pattern is an interference effect (Bragg reflection from crystallite planes), which only waves produce.
  - The ring diameters scale as U^(−1/2), exactly as λ = h/p predicts.
  - The d values obtained agree with the graphite spacings known from X-ray crystallography.
  - The rings are made by electrons: a magnetic field displaces them. Mention this only as an argument; do not do it without permission.
- **Q5 (is the approximation valid for D = 6 cm?)**
  - tan 2θ = 3/13.5 ≈ 0.2222, so 2θ ≈ 12.53°.
  - 2·sin θ ≈ 0.2183, while D/(2L) ≈ 0.2222.
  - The approximation is therefore off by about **1.8%**, which makes d about 1.8% **too small**.
  - Compare this with the experimental uncertainty. It is borderline: acceptable for a rough result, but correctable with the exact formula. The engine computes it.
- **Q6 (dependence of D on U^(−1/2)).** **Direct proportionality, a linear relation through the origin:** D = (C/d)·U^(−1/2).
- **Q7 (linear relation between U and a power of D).**
  - **x = −2.** U = (C²/d²)·D⁻², so U plotted against D⁻² is a straight line through the origin.
  - The slope is m = C²/d², so **d = C/√m**.
