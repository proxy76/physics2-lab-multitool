# Lab Companion: Physics 2

A phone-first web app (PWA) for running and analysing **Experiments 5, 6, 7, 3 and 4** of the Physics 2 laboratory guide (`LaboratoryGuide.pdf`). It is built for a team of three and follows the order the team runs the labs in.

- **Run guides.** Each experiment has one step per card, a role tag (OP operator, RD reader, AN analyst), safety notes, timers and "meanwhile" tasks. You type each number on the same card where it is produced, and a one-screen cheat card summarises the whole procedure.
- **Analysis.** The guide's method and tables come with show-your-work steps and the lab's rounding rule. All arithmetic uses 50-digit mpmath inside a Web Worker. Advanced cross-checks (exact geometry, weighted fits, counting-statistics σ) are clearly labelled.
- **Answers.** There is an answer for every question in sections X.8. Every number in them is generated by the engine. Answers that depend on the team's data fill in from the active session.
- **Calculator.** Generic tools G1–G8: statistics, counting, least squares, propagation (SymPy), the graphical method, report and compare, units and constants, and decay correction.
- **Lab-proof.** After the first load the app works fully offline, including the Python engine. Data autosaves on every edit. A link or QR code moves a session to another phone with no server involved. Dark and dark-room themes are included.

The design brief is `LAB_COMPANION_AGENT_BRIEF.md`. The working documents are in `docs/`:

| File | What it is |
|---|---|
| `docs/PDF_ANALYSIS.md` | Coverage checklist: every step, table, analysis item and question of Exp. 3–7 |
| `docs/ERRATA.md` | Where the guide is wrong, and what the app does instead (also shown in-app as "Guide notes") |
| `docs/DECISIONS.md` | Design decisions D1–D22, with the alternatives considered |
| `docs/SOURCES.md` | CODATA 2022, NIST XCOM/ASD/StRD and NNDC values, with URLs and access dates |

## Repository layout

```

  labcalc/experiments/exp3.py … exp7.py
  tests/           pytest: NIST StRD, numpy/scipy/uncertainties cross-checks, golden datasets, snapshots

  src/worker/      Pyodide bootstrap (the engine runs in a Web Worker)
  src/content/     run guides, answers, guide notes; generated/ holds engine-made JSON

```

## Develop

Requirements: Node 24, Python 3.12+.

```bash
# engine
cd engine
python -m venv .venv && . .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -e ".[test]"
pytest -q -m "not slow"          # about 15 s; `pytest -m slow` runs the 1000-trial coverage tests

# web
cd web
npm ci
npm run dev                      # http://localhost:5173 (copies Pyodide, fetches pinned wheels, zips the engine)
```

The browser runs the same `labcalc` sources: `npm run dev` and `npm run build` zip `engine/labcalc` into `public/py/labcalc.zip`. Editing the Python therefore only needs a reload.

### Tests

| Command (in `web/` unless noted) | What it checks |
|---|---|
| `pytest` (in `engine/`) | NIST StRD Norris/NoInt1/NoInt2 to ≥ 12 digits, cross-checks with numpy/scipy/uncertainties, golden datasets (zero noise → 30 digits; noisy → honest coverage), rounding and parser cases, dps 50 vs 100, answer snapshots |
| `npm test` | Vitest: string-only digit rounding, input parser mirror, share links, CSV/Markdown/LaTeX export, store, timers; every guide/answer formula compiles in KaTeX |
| `npm run test:pyodide` | The engine inside the real Pyodide runtime, including the lazy SymPy load |
| `npm run build && npm run e2e` | Playwright on two phone viewports: offline after one load, autosave across reload and tab close, share link to a second phone, entry from the Run screen, headline results for all five experiments, no sideways scrolling, 48 px targets, plot export, and the production Content-Security-Policy |
| `npm run screens` | Screenshots of every screen in each theme, for visual review (needs `npm run preview` running) |

To run the e2e suite against another server (for example the real Caddy config), set `BASE_URL=http://localhost:8088/`.

### Regenerating engine-made content

The answers and example datasets are produced by the engine and committed. A pytest snapshot fails if they drift.

```bash
cd engine
python -m labcalc.answers > ../web/src/content/generated/answers.json
python -m labcalc.golden  > ../web/src/content/generated/examples.json
```

On Windows, set `PYTHONIOENCODING=utf-8` first. The JSON contains symbols such as σ and ², which the default console encoding cannot write.

## Deploy (Ubuntu VM on Proxmox, Caddy)

The site is static: `web/dist` after `npm run build`. It must be served over **HTTPS**, because the service worker (offline mode), the Wake Lock API and "Add to home screen" need a secure origin. Caddy obtains and renews the certificate automatically.

1. Point the domain's DNS A/AAAA record at the VM, and forward ports 80 and 443 to it.
2. From your machine, with SSH access to the VM:

   ```bash
   export DEPLOY_HOST=ubuntu@<vm-address> LAB_DOMAIN=lab.example.org
   deploy/deploy.sh setup     # once: installs Caddy, installs deploy/Caddyfile, sets the domain
   deploy/deploy.sh           # every release: npm ci + build, then rsync to /srv/lab-companion
   ```

   You can put these variables in `deploy/.env` instead. That file is git-ignored.
3. Open the site on each phone once while online. When the header shows **Offline ready**, the phone works in airplane mode. To install the app, use "Add to home screen".

After a new deploy, phones show an **Update** button on their next visit. Updating keeps all saved data.

Alternatives:

- **Docker.** Run `docker build -f deploy/Dockerfile -t lab-companion .`, then `docker run -d -p 80:80 -p 443:443 -e LAB_DOMAIN=lab.example.org -v caddy_data:/data lab-companion`.
- **nginx.** Use `deploy/nginx.conf` with certbot. It has the same headers and caching as the Caddyfile.
- **Private site.** Uncomment the `basic_auth` block in the Caddyfile, or `auth_basic` in the nginx config.

Caching: `/assets/*` (hashed) is immutable. Everything else is revalidated (`no-cache`), so a deploy is picked up immediately. `.wasm` is served as `application/wasm`.

## Before the first lab

- Load each experiment's **example data** (Session → Load example data) and walk through its Run, Data and Results tabs once. Delete the example sessions afterwards.
- The **Verify in lab** checkboxes mark apparatus details that could not be confirmed from the guide or online: the counter model and its preset switches, the rack slots, the CASSY settings, and the letters in Fig. 7.1. Tick them off on the day.
- Settings → **This phone's role** highlights each person's steps. Use **Constants → Guide's rounded values** only to reproduce the guide's own numbers.
