# Decisions

Format: decision — why — alternatives considered. Newest decisions are appended at the end.

## D1. Engine in Python + mpmath, run in the browser with Pyodide (Web Worker)

- **Why.** Arbitrary precision (mp.dps = 50) removes floating-point error from the result path; the exact same code is verified natively by pytest (NIST StRD, numpy/scipy/uncertainties cross-checks) and executed in the browser, so "what was tested is what runs". Works fully offline after first load; no server state, nothing to keep alive on the VM.
- **Alternatives.**
  - *FastAPI backend on the VM.* Simplest engine deployment, but the lab Wi-Fi is unreliable and the app must compute offline → rejected for the result path. (The static build could still be served next to an API later.)
  - *TypeScript + decimal.js.* Small and fast to start, but no symbolic differentiation (custom propagation), no mature test cross-checks, and the engine would have to be written and validated twice.
- **Cost.** ≈ 13 MB first download (Pyodide core + stdlib + mpmath + labcalc), 2–5 s warm-up on a phone. Mitigated: the worker starts warming on app open, an "Engine" status pill is shown, guides/answers/data entry never wait for it (answers are pre-generated JSON, see D6). SymPy (≈ 7 MB) is loaded only when the custom-expression propagation tool is opened.

## D2. Versions

- Pyodide **314.0.7** (CPython 3.14 in WebAssembly) in the browser; native tests run on CPython 3.12 (the brief's version) and CI also runs 3.14. The engine is pure Python with no version-specific syntax.
- **mpmath 1.3.0** pinned everywhere (SymPy 1.14 requires mpmath < 1.4).
- **SymPy 1.14.0** (lazy).
- Wheels are downloaded from PyPI at build time with pinned SHA-256 (`web/scripts/fetch-py.mjs`) and self-hosted under `/py/`, then precached by the service worker. No CDN at lab time.

## D3. Charts: own SVG plot component instead of uPlot/Chart.js

- **Why.** We need error bars, a residual panel under every fit, highlighted outliers, a fitted curve for the exact solid-angle model, and **report-ready SVG/PNG export with axis titles and units**. A ~300-line React SVG component does exactly that, renders identically in export, scales crisply, needs no canvas-to-SVG conversion and adds ~0 kB of dependencies. Touch: tap a point to see its value and residual.
- **Alternatives.** uPlot (canvas; error bars and SVG export need plugins), Chart.js (heavier, canvas-only export). The brief allowed "pick one"; a purpose-built SVG component is lighter than either and is recorded here as a deliberate deviation.

## D4. Hosting: static build on a Proxmox Ubuntu VM behind Caddy

- The repository is private. The production target is an Ubuntu VM on the team's Proxmox host, serving the static `web/dist` with **Caddy** (automatic HTTPS via Let's Encrypt — required for the service worker, Wake Lock and installability). `deploy/` contains a Caddyfile, an nginx alternative, a Dockerfile (multi-stage build → Caddy) and a `deploy.sh` (build + rsync). Optional HTTP basic auth is included (commented) to keep the site closed to the team.
- `.wasm` must be served as `application/wasm`; `/py/*` and hashed assets get long-lived immutable caching; `index.html`, `sw.js` and the manifest are `no-cache`.

## D5. Numbers cross the worker boundary only as strings

UI collects strings; `labcalc.parse` turns them into `mpf` exactly (decimal comma, `×10^`, `e`, Unicode minus all accepted). Results come back as decimal strings (≈ 30 significant digits) plus a `report` string formatted with the lab's rounding rule. JavaScript only converts to `Number` to place points on a chart.

## D6. Answers are generated by the engine at build time and frozen

`python -m labcalc.answers > web/src/content/generated/answers.json`. A pytest snapshot test (`tests/test_answers_snapshot.py`) regenerates the JSON and fails if it differs from the committed file, so no answer number can drift silently. Data-dependent answers (Exp 5 Q6 error table, Exp 6 Q3/Q6, Exp 7 Q6) are produced live by `expN.analyze` from the team's data.

## D7. Rounding rule implementation

`decimal` with `ROUND_HALF_UP`. Significant digits of the uncertainty are chosen from the **leading digit of the unrounded uncertainty** (1 → two digits, else one); if rounding carries (0.096 → 0.1) the carried value is kept (0.1 has leading digit 1 but is *not* re-expanded to 0.10 — the decision was made on the unrounded value). The value is rounded to the same decimal position. Scientific notation with a shared exponent chosen from the value. Optional "round uncertainty up" (GUM 7.2.6 permits it).

## D8. Least-squares implementation

Centred two-pass sums (Σ(xᵢ − x̄)², Σ(xᵢ − x̄)(yᵢ − ȳ)) at mp.dps = 50 for the numbers; the "show steps" panel displays the guide's raw-sum forms B.6–B.11 with the same values, since they are algebraically identical. Through-origin: s_a² = SSR/((n − 1)Σx²) (NIST NoInt convention). Weighted: internal σ (from σᵢ) and external σ (× √χ²_red) both reported. cov(a, b) = −x̄·s_a² (unweighted).

## D9. Experiment 5, Method I

The guide asks to "estimate the activity from the graph n = f(r) using the answer to Q4" (Ω/4π → ½ at r = 0). The headline Method I fits the exact geometric model n = K·g(r), g(r) = ½ − 1/√(4 + (D/r)²) (one-parameter least squares through the origin, unweighted to match the guide's LSQ convention) and reports n(0) = K/2 and Λ_I = 2·n(0)/(εS) = K/(εS) with σ from the fit. A free-hand option (student's own extrapolated n(0)) is also provided. Extrapolating the D²/16r² law is impossible (it diverges at r = 0); the UI explains why.

## D10. Experiment 3 sign convention and units

Calibration fits x (mm) against X = λ⁻² with λ in nm (so B is in mm·nm²) — the numbers stay readable on the plot and in the student's report; the engine converts to SI internally for R. The Rydberg fit uses y = 1/λ in m⁻¹ and X = 1/n². R_H = −a; σ_R = s_a. Hα and Hε are outside the calibration range (404.7–623.4 nm) and get an extrapolation warning.

## D11. Experiment 4 fit

Headline: least squares D = k·U^(−1/2) + b (the guide's Appendix-B line, intercept allowed), d = C/k, σ_d = d·s_k/k with C treated as exact. Through-origin fit and the Q7 linearisation U = (C²/d²)·D⁻² are shown as cross-checks. C defaults to CODATA (3.3112×10⁻¹⁰ m·V^½); "Guide constants" uses 3.3×10⁻¹⁰.

## D12. Experiment 6

Rate = Area/t with Area = ½(R − L)·H (Fig. 6.4 triangle). Fit y = ln(rate) vs x (cm): μ = −a, σ_μ = s_a. μ/ρ uses NIST densities (treated as exact). If all times are equal, using ln(Area) gives the same μ; the app always divides by t. An optional ln(I/I₀) column is shown for the report.

## D13. Experiment 7

Fit U₀ (V) vs ν (Hz); h = e·a, W = −e·b, ν₀ = −b/a with σ from the full covariance; λ_max = c/ν₀. Filter wavelengths default to the guide's §7.3.2 list (yellow 578.2 nm). U₀ per filter = mean of readings, σ = s/√N (Q3). Weighted fit (σ = SEM) is in Advanced only.

## D14. Type-B convention for instrument resolution

Default: ± half the least count (what students are usually taught), with the GUM rectangular value δ/(2√3) shown next to it. Stated explicitly wherever used (Exp 6 Q2, Exp 3 σ_x, Exp 4 σ_D).

## D15. Monte Carlo

Pure-Python floats with a seeded `random.Random` (default 2×10⁵ samples in the browser, 10⁶ allowed). Statistical, not part of the headline path, so float precision is appropriate. Warns if MC σ differs from linear propagation by more than 10 %.

## D16. Frontend stack

Vite + React + TypeScript, plain CSS with design tokens (no Tailwind: the token system is small and hand-tuned for the dark-room theme), KaTeX for formulas, idb-keyval for IndexedDB autosave, lz-string for share links, `qrcode` for QR codes, `vite-plugin-pwa` (Workbox) for offline precaching.
